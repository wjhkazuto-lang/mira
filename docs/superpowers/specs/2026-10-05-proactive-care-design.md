# Mira 主动关心（主动消息）设计文档

- 日期：2026-10-05
- 状态：已通过（2026-10-05）；实施计划：`docs/superpowers/plans/2026-10-05-proactive-care.md`
- 范围：主动消息（v2 的第一块）——打开 App 时先说、Mac 系统通知、每周信

## 1. 目标

| # | 需求 | 来源 |
|---|---|---|
| P1 | 打开 App 时，Mira 在"值得开口"时先说话；没什么可说的就沉默 | 用户（10-04 路线） |
| P2 | Mira 运行中（窗口开着、可能不在前台）值得开口时，发 Mac 系统通知；通知上显示具体内容 | 用户 |
| P3 | 每周日 20:00 前后发一封"每周信"（回顾这周 + 提醒下周） | 用户 |
| P4 | 允许开口的时机（四个都要）：承诺到期没动静 / 超过 2 天没聊 / 情绪事件回访 / 目标长时间没动静 | 用户多选 |
| P5 | 不烦人：一天最多一条、安静时段闭嘴、同一条承诺/目标不反复提、用户在场或正在聊时绝不插话 | 设计原则（v1 设计 R10：不要定时问候） |

用户已确认的决定：三件一起设计、分三步实现；通知显示具体内容；四种开口时机都要；每周信在周日晚 20:00。

**不做**（YAGNI）：关着窗口也能收到通知（需要 Mira 常驻/菜单栏模式，属于路线第 3 项，以后单独设计）；iMessage/Telegram 入口；开机自启；主动消息的专属界面样式（先按普通气泡显示）；设置界面（用 `.env`）。

**成功标准**：

- 隔天打开 App：聊天里有时已经有一句 Mira 先说的话，跟承诺/目标/最近的事有关；没值得说的时候和现在完全一样。
- 窗口开着但在后台：承诺到期或久没聊时会收到 Mac 通知（显示具体一句），点通知回到 Mira 窗口。
- 周日 20:00 前后聊天里出现一封每周信。
- 连用几天不出现"打卡式"的废话；主动消息每天 ≤1 条（每周信当天可以 +1）。
- 把 `PROACTIVE` 设成 0 后，行为与现在完全一致（随时可退）。

## 2. 总体思路

**便宜的先判断，值得了才花钱。**

```
tick（每 30 秒）/ App 启动
  └─ 闸门（纯规则，几个 SQL 查询，不花钱）：
     开关 → 安静时段 → 距上次用户消息够久 → 今天没开口过
     → 最后一条不是"没人应的主动消息" → 距上次评估够久 → Mira 没在回复中
       └─ 收集候选（免费）：到期的承诺 / 够久没聊 / 最近的情绪事件 / 很久没动静的目标
            ├─ 没候选 → 沉默（记下评估时间，直接结束）
            └─ 有候选 → 调模型（唯一花钱的一步）：值不值得开口 + 怎么说
                 ├─ speak=false → 沉默（沉默是完全正常的输出）
                 └─ speak=true → 复查用户没回来 → 存进聊天 + 广播气泡 + 发系统通知
```

**沉默是常态**：宁可不说，也不说没营养的话。这一条要写进提示词里。

## 3. 决策引擎（新建 `mira/proactive.py`）

### 3.1 闸门（全部通过才继续，纯规则）

1. `PROACTIVE=1`（开发模式默认关）。
2. 不在安静时段（默认 22:00–08:00）。
3. 距最后一条**用户**消息 ≥ 4 小时（常数）——人在场时，聊天本身会把该说的说掉，不需要"主动"。
4. 今天开口次数 < `PROACTIVE_MAX_PER_DAY`（默认 1；每周信不算在内）。
5. 最后一条消息不是"没被回应的主动消息"——Mira 说了没人应，就不追问（用户回任何一句即解除）。
6. 距上次评估 ≥ 4 小时（常数）——候选挂着时不要每 30 秒去问一次模型，会白花钱。
7. Mira 当前没有正在进行的回复/重试（不插话）。

### 3.2 候选收集（SQL，免费）

| 候选 | 条件（常数写在代码里） | 重复限制 |
|---|---|---|
| 承诺到期没动静 | open 的 commitment，`due_at` ≤ 今天 | 同一条 3 天内不重复提 |
| 好久没聊 | 距最后一条用户消息 ≥ 2 天 | 天然受"每天一条"限制 |
| 情绪回访 | 最近 72 小时内的 episode | 每个事件只回访一次 |
| 目标轻推 | open 的 goal，`updated_at` 距今 ≥ 14 天 | 同一个目标 14 天内不重复 |

没有候选就不调模型，只记评估时间。

### 3.3 模型决策（新建提示词 `mira/prompts/proactive.md`）

给模型：现在的时间、距上次聊天多久、最近一段对话、候选列表（各候选的时间与背景）、检索到的相关记忆、核心档案。

输出 JSON：`{"speak": bool, "kind": "...", "reason": "一句话", "messages": ["..."], "expression": "..."}`

提示词约束：一次只说一件事；宁愿不说也别硬找话；不编造经历；不说教；1–3 条短气泡（和聊天一样拆句）；语气和平时聊天一致。模型用 `chat_model`、`chat_temperature`——同一个人说话，温度也照旧。

### 3.4 开口（决定要说的时候）

1. **复查**（模型调用要几秒，期间用户可能已经回来聊上了）：距用户消息仍 ≥ 4 小时、Mira 仍空闲，否则放弃这次开口（什么都不记，下次评估再说）。
2. 存消息：`add_message("assistant", text, meta={"proactive": {"kind": …, "reason": …}})`——就是一条普通助手消息，聊天页按普通气泡显示，**前端零改动**。
3. 广播：连着的页面先收 `typing` 再收 `bubble`（复用现有事件格式）——打开 App 后会看到 Mira"正在输入"，然后开口。
4. 发通知（第 4 节）。
5. 写入 `proactive_log`（kind、指向哪条记忆/事件、时间）。

### 3.5 写入器的触发条件要跟着改

主动消息是助手消息。如果沿用"有未处理消息就让写入器跑"的判断（`unprocessed_messages()`），没人回的时候写入器会单独把 Mira 自己的话送去整理——白花钱还产生杂讯。改法：

- 新增 `Store.unprocessed_user_messages()` / `pending_user_message_count()`；
- `Scheduler.startup()` / `tick()` 的写入器触发、`status()` 的"等待中"都改用"未处理的**用户**消息"判断；
- 主动消息保持未处理：等用户回复后，写入器把"Mira 先说的 + 用户回的"当一段完整对话一起整理，上下文不缺；
- 聊天上下文的"距上次聊天"（`context.py` 的 `last_chat_at`）改为按最后一条**用户**消息算——否则刚开口的主动消息会把"好久没聊"顶掉。

### 3.6 调度接入（`mira/scheduler.py`）

- 新任务 `proactive`：用主锁（和写入器/反思器串行，不并发动聊天记录）；失败退避 30 分钟（复用 `FAILURE_BACKOFF`）。失败只记日志、不进状态页——错过一次打招呼不是事故。
- `startup()` 顺序：写入器补跑 → **主动检查** → 反思器补跑（昨晚的话先变成记忆，"打开先说"才有准头；档案略旧无妨）。这就是桌面版的"打开时先说"：窗口刚加载好聊天页，话刚好在那；也可能过几秒实时冒出来，都自然。
- `tick()`：每轮先过闸门（便宜），过了才进 `_run`。
- 时间、次数、冷却全部落在 `job_state` + `proactive_log`，重启不丢。

### 3.7 每周信（第三步实现）

- 独立调度：周日（`WEEKLY_LETTER_WEEKDAY`，默认 6）的 `WEEKLY_LETTER_HOUR`（默认 20 点）；`job_state("weekly_letter")` 记上次，距今 <6 天不重复；错过了（周日晚 Mac 睡着）下次开机补发。
- 内容用单独提示词 `mira/prompts/weekly.md`：这周的 episode、新建的记忆、承诺/目标进展、核心档案 → 2–4 条气泡，像一封信：这周印象最深的事、看到的变化、一句下周的提醒或关心。
- 不受"每天一条"限制、不参与冷却；发完就是普通消息，用户回它照常聊。

## 4. Mac 通知（新建 `mira/notify.py`，第二步实现）

- `MacNotifier`：pyobjc 的 `UserNotifications`（pywebview 自带 pyobjc）。首次使用时请求一次权限；`notify(title, body)` 弹通知，正文 = 第一条气泡的文本（截短到约 120 字）；点通知 → 激活 Mira 窗口（pyobjc 激活 + pywebview 窗口前置，回调由 `desktop.py` 传入）。
- 只在 Mira.app（bundle 模式）里启用：用 `NSBundle.mainBundle().bundleIdentifier()` 判断（`local.mira.desktop`）；终端模式用 `NullNotifier`（消息照常进聊天，只是不弹）。
- `NOTIFICATIONS=0` 可关；权限被拒 → 记一次日志，静默降级成"只进聊天"。
- 通知里显示具体内容（用户已确认）。
- **待实测**：未签名的 Mira.app 能不能正常发系统通知（macOS 对通知来源有要求）。第一步先在真 App 里发一条测试通知验证；不行就退到备选：Dock 图标跳动（`requestUserAttention`）+ 徽标数字，点 Dock 图标回到窗口。结果如实写进 README 和交接文档。

## 5. 配置（`.env` 新增，都有默认值）

| 键 | 默认 | 说明 |
|---|---|---|
| `PROACTIVE` | 1 | 主动关心总开关（开发模式默认 0） |
| `PROACTIVE_MAX_PER_DAY` | 1 | 每天最多几条（每周信不算） |
| `PROACTIVE_QUIET_HOURS` | 22-8 | 安静时段：不开口、不通知 |
| `WEEKLY_LETTER_WEEKDAY` | 6 | 0=周一 … 6=周日 |
| `WEEKLY_LETTER_HOUR` | 20 | 几点发每周信 |
| `NOTIFICATIONS` | 1 | 0 = 只进聊天、不弹系统通知 |

其余常数（4 小时在场间隔、4 小时评估间隔、3 天承诺冷却、14 天目标冷却、72 小时事件窗口、2 天算"好久没聊"）先写在代码里，真需要再升级成配置。

## 6. 存储（`mira/store.py`）

- 新表 `proactive_log(id, kind, ref_type, ref_id, created_at)`：每日上限、重复冷却、"这个事件回访过没有"都查它。
- SCHEMA 里加 `CREATE TABLE IF NOT EXISTS`（每次打开库都会执行，旧库自动补表，无需迁移）；`SCHEMA_VERSION` 1 → 2。
- 新方法：`add_proactive_log()`、`last_proactive_at()`、`count_proactive_on(day)`、`proactive_since(ref_type, ref_id)`、`unprocessed_user_messages()`、`pending_user_message_count()`。

## 7. 测试

**单元测试（假 LLM、假时钟、假通知器，不花钱）**

- 闸门：安静时段、今天已开口、评估间隔内、人在场（<4 小时）、最后一条是没被回应的主动消息 → 都不开口；开关关闭 → 完全不动。
- 候选：到期承诺、2 天未聊、72 小时事件、14 天目标各自出现/不出现；冷却期内不重复。
- 开口：消息带 `meta.proactive`；`typing` + `bubble` 事件广播；假通知器恰好被调一次；用户正在聊（Mira 忙）时放弃。
- 写入器联动：只有主动消息时写入器不跑、状态不显示"等待中"；用户回复后两者一起被整理。
- 每周信：周日 20 点触发、<6 天不重复、错过补发（固定时钟）。
- 通知：`NullNotifier` 不炸；`NOTIFICATIONS=0` 时不调用。
- 原有 339 个测试全部保持通过——写入器"把助手回复和用户消息一起整理"的现有行为不能变。

**评测（真实 API，约几分钱，人工运行）**

- 新增一组主动消息场景：a) 承诺逾期 + 两天没聊 → 开口，且只提这一件；b) 风平浪静 → 沉默；c) 前一天的情绪事件 → 次日温暖回访；d) 刚聊过（用户在场）→ 沉默（规则层，不调 API）。
- 每周信一个场景：给一周素材 → 像封信、不流水账、不编造。

**实测（开发模式 `dev.db`，绝不连真实库）**

- 假模型下打开桌面 App：确认机制不误伤正常聊天。
- 真机 + 真 API：临时把评估间隔调小，验证一次真实开口和一条真实通知；记录通知的实际效果（权限弹窗、外观、点击激活）。
